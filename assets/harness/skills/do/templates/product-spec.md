# Product Spec Template

Planner Agent가 생성하는 Product Spec의 표준 템플릿.

```markdown
## Product Spec: {TASK_DESCRIPTION}

### 문제 정의
- 왜 이 기능이 필요한가
- 사용자 관점의 가치

### AI 기능 제안 (선택)
> 이 섹션은 TASK_DESCRIPTION에 AI 활용 가능성이 있을 때만 포함한다.
> 사용자가 승인해야 계획에 포함된다.

- 제안 1: {설명} — 근거: {왜 이 기능에 AI가 적합한가}
- 제안 2: {설명} — 근거: {왜 이 기능에 AI가 적합한가}

### 기능 명세
- [ ] 기능 1: {설명} — 검증: {어떻게 확인}
- [ ] 기능 2: {설명} — 검증: {어떻게 확인}

### 설계 검토
- 아키텍처: {선택한 접근 방식과 근거}
- 대안: {검토 후 기각한 접근 방식과 기각 이유}
- Context Module 준수: {적용 패턴 목록}
- 설계 결정: {Design Validator가 확인한 핵심 결정 목록}

### Sprint 분할

Sprint 1 (Core):
  T0. Tests (Red Phase)
    - [ ] {테스트 파일}: {테스트 케이스} — Done when: {구체적 pass 조건}
  T1. Type Definitions
    - [ ] {구체적 작업}
  T2. Database (해당 시)
    - [ ] {구체적 작업}
  T3. Server
    - [ ] {구체적 작업}
  T4. Client (해당 시)
    - [ ] {구체적 작업}
  E2E 검증:
    - [ ] {브라우저에서 확인할 시나리오}

Sprint 2 (Enhancement):
  parallel: true    # 같은 레벨 Sprint와 병렬 실행 허용 (생략 시 순차)
  depends_on: []    # 의존 Sprint 번호 목록 (빈 배열 = 의존 없음, 예: [1] = Sprint 1 완료 후)
  T0~T4 + E2E 동일 구조

### 데이터 수명주기

> 이 섹션은 새로운 데이터를 생성/계산하는 기능이 있을 때만 포함한다.

| 데이터 | 생성(Compute) | 저장(Store) | 노출(Expose) | 소비(Consume) |
|--------|--------------|-------------|-------------|--------------|
| {데이터명} | {service/worker 등} | {DB 컬럼/테이블} | {API 엔드포인트} | {UI 컴포넌트/외부 시스템} |

### 완료 기준 (Acceptance Criteria)
- [ ] {검증 가능한 완료 기준 1}
- [ ] {검증 가능한 완료 기준 2}

#### 자동 검증 기준 (모든 Spec에 자동 포함)
- [ ] 새로 생성된 모든 데이터의 최종 소비자가 구현되었거나 "스코프 외"에 명시됨
- [ ] 사용자 대면 한국어 텍스트의 조사(이/가, 은/는 등)가 문맥에 맞게 정확함

### 기술 결정
- {아키텍처 선택과 근거}

### 스코프 외 — 별도 작업 (Deferred)
> 이 섹션은 분석 과정에서 식별되었으나 이번 스코프에서 제외한 항목이 있을 때만 포함한다.
> 제외 항목이 없으면 이 섹션을 생략한다.

| ID | 이슈 | 제외 이유 | 해결 방향 |
|----|------|-----------|-----------|
| {ID} | {이슈 요약} | {코드 버그가 아닌 이유, 별도 feature인 이유} | {향후 해결 시 접근 방향} |
```

## Sprint 분할 기준

| 조건 | Sprint 전략 |
|------|-------------|
| 영향 파일 < 5개 | 단일 Sprint (분할 불필요) |
| 영향 파일 5~8개 | 2 Sprint (Core + Enhancement) |
| 영향 파일 ≥ 9개 또는 새 도메인 | 3+ Sprint (기능 단위 분할) |

각 Sprint는 독립적으로 배포 가능한 단위여야 한다. Sprint N이 완료되면 코드는 merge-ready 상태.

### 병렬 Sprint 선언 규칙

| 조건 | 선언 방식 |
|------|----------|
| 두 Sprint가 완전히 다른 파일을 수정 | `parallel: true`, `depends_on: []` |
| Enhancement가 Core 결과물에 의존 | 두 필드 생략 (기본 순차) |
| 명시적 이전 Sprint 의존 | `depends_on: [1]` (Sprint 1 완료 후 실행) |

> **주의**: `parallel: true`로 선언한 Sprint들은 서로 수정 파일이 겹치지 않아야 한다.
> Orchestrator가 실행 전 파일 중복을 자동 검사하여 겹치는 Sprint 쌍은 순차 처리로 강등한다.
