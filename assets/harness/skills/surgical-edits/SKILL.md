# Surgical Edits — 변경 범위 단속

요청한 변경에만 손대고, 인접 코드는 건드리지 않는다. 모든 변경된 줄은 사용자 요청과 직접 연결되어야 한다.

## 핵심 규칙

1. **인접 코드 "개선" 금지** — 주석·포매팅·변수명·docstring을 요청 없이 손대지 마라.
2. **요청 없는 리팩터링 금지** — 망가지지 않은 것을 고치지 마라.
3. **기존 스타일 매칭** — single/double quote, 4/2 space indent, type hint 유무, snake/camel case는 파일이 쓰는 방식 그대로 유지하라. 본인 취향이 다르더라도 그대로 둔다.
4. **dead code는 언급만, 삭제 금지** — 무관한 dead code를 발견하면 마지막 응답에 한 줄 언급하고, 사용자가 명시적으로 요청하지 않는 한 삭제하지 마라.
5. **본인 변경이 만든 orphan만 정리** — 본인 수정으로 unused가 된 import·변수만 제거하고, 사전부터 unused였던 것은 건드리지 마라.

## 자가 점검 질문

작업을 끝내기 전, diff를 보고 다음을 자문하라:

> **"이 줄이 사용자 요청을 어떻게 직접 만족시키는가?"**

설명이 1초 안에 떠오르지 않는 줄이 있다면 되돌려라.

## 위반 사례 (즉시 되돌릴 것)

- 버그 픽스 요청에 무관한 검증 로직 추가
- "로깅 추가" 요청에 따옴표 스타일·boolean 반환·예외 처리 동시 변경
- "함수 X 수정" 요청에 인접한 함수 Y의 주석을 더 명확히 다시 씀
- "import 정리" 요청에 함수 순서까지 재배열
- 작업 도중 발견한 무관한 dead variable·import 삭제

## 예외 (이 규칙이 적용되지 않는 경우)

- 사용자가 명시적으로 **"리팩터해줘"·"포매팅 통일해줘"·"전체 스타일 맞춰줘"** 등 범위 확장을 요청한 경우
- **Biome auto-fix**가 강제하는 변경 — project pre-commit 규칙이므로 그대로 둔다. (의도치 않은 줄 변경이 Biome auto-fix 때문이면 그건 정상.)
- **`/specify`·`/do` 같은 구조화 워크플로우**가 스스로 정의한 범위 안의 변경 — 해당 워크플로우의 plan이 우선한다.

## 의심스러우면 멈추고 물어라

- 인접 코드의 명백한 문제를 발견했지만 요청 범위 밖이라면: 작업 완료 후 한 줄로 보고하고 사용자에게 별개 작업으로 처리할지 묻는다.
- "이것도 같이 고치는 게 자연스러워 보임"이라는 충동이 들면, 그 자체로 신호다. 묻고 진행하라.

## 적용 시점

- 명시적 단일 편집 요청 (예: "X 함수에 Y 추가", "Z 버그 픽스", "import 한 줄 추가")
- 좁은 스코프의 버그 픽스
- 작은 기능 추가

명시적으로 넓은 스코프(전체 리팩터·마이그레이션·페이지 신규 구현 등)가 정해진 작업에서는 이 규칙보다 해당 작업의 plan이 우선한다.
